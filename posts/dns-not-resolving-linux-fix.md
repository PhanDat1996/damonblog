`curl: (6) Could not resolve host: api.example.com`. Or `ping: api.example.com: Temporary failure in name resolution`. You run `dig api.example.com`, it returns an IP, and now you have two tools disagreeing about the same name.

That disagreement is the most useful clue you have. Name resolution on Linux goes through several layers: the application, glibc's resolver, `/etc/nsswitch.conf`, `/etc/hosts`, often a local stub like systemd-resolved, and finally an upstream DNS server. Overwriting `/etc/resolv.conf` with `8.8.8.8` fixes one of those layers and can break another (internal names, cloud private zones). Find the broken layer first.

---

## TL;DR

```bash
getent ahosts api.example.com          # what applications actually get
dig api.example.com                    # what the configured DNS server says
dig @1.1.1.1 api.example.com           # bypass your config entirely

ls -l /etc/resolv.conf                 # who manages this file?
resolvectl status                      # systemd-resolved: real upstream servers

resolvectl flush-caches                # after fixing, clear the local cache
```

If `getent` fails but `dig` works, the problem is on the box (nsswitch, hosts file, search domains, the local stub). If both fail but `dig @1.1.1.1` works, your configured DNS server is the problem. If everything fails, it's the network path to port 53.

## Read the error first

| Message | What it means |
|---|---|
| `Temporary failure in name resolution` | `EAI_AGAIN`: no usable answer. The nameserver timed out, was unreachable, or returned `SERVFAIL` |
| `Name or service not known` | `EAI_NONAME`: a server answered, and the name does not exist (`NXDOMAIN`), or no source in `nsswitch.conf` had it |
| `curl: (6) Could not resolve host` | curl's wrapper around either of the above. Check with `getent` |
| `dig`: `status: SERVFAIL` | The server you asked could not get an answer, often a broken upstream or DNSSEC validation failure |
| `dig`: `connection timed out; no servers could be reached` | Nothing answered on port 53. Think network, firewall, or a dead stub resolver |

"Temporary failure" points at reachability. "Not known" points at the name or the search domain. They send you in different directions.

## Why `dig` and your application disagree

`dig` and `nslookup` are DNS clients. They read the `nameserver` lines in `/etc/resolv.conf` and send a DNS packet. They do **not** use:

- `/etc/hosts`
- `/etc/nsswitch.conf` (the order of `files`, `resolve`, `dns`, `myhostname`…)
- `search` domains (`dig` ignores them unless you pass `+search`)

Applications call `getaddrinfo()`, which goes through all of that. So test the way applications resolve:

```bash
getent ahosts api.example.com
# 10.20.1.15      STREAM api.example.com
# 10.20.1.15      DGRAM
# 10.20.1.15      RAW

grep ^hosts /etc/nsswitch.conf
# hosts: files mdns4_minimal [NOTFOUND=return] dns
```

Common causes when `dig` works and `getent` doesn't:

- A stale entry in `/etc/hosts` overriding DNS (`files` comes first).
- A short name like `db01` that only resolves with the right `search` domain.
- `mdns4_minimal [NOTFOUND=return]` stopping lookups for names ending in `.local` before DNS is ever asked. If your internal domain really is `.local`, this bites.

## Step 1: Who owns `/etc/resolv.conf`?

```bash
ls -l /etc/resolv.conf
cat /etc/resolv.conf
```

| What you see | Who manages it | Where to make the real fix |
|---|---|---|
| Symlink to `/run/systemd/resolve/stub-resolv.conf`, `nameserver 127.0.0.53` | systemd-resolved (Ubuntu 18.04+, Fedora 33+) | netplan / NetworkManager / `resolved.conf` |
| `# Generated by NetworkManager` | NetworkManager (RHEL, Rocky, Alma, desktops) | `nmcli` |
| Plain file, no header | Nobody (or cloud-init/DHCP client on boot) | The file itself, or the DHCP config |

On a systemd-resolved system, `127.0.0.53` is a local stub. It is not the server that does the lookup. To see the real upstream:

```bash
resolvectl status
# Link 2 (eth0)
#     Current Scopes: DNS
#          Protocols: +DefaultRoute -LLMNR -mDNS -DNSOverTLS DNSSEC=no/unsupported
# Current DNS Server: 10.0.0.2
#        DNS Servers: 10.0.0.2
#         DNS Domain: ec2.internal
```

On older systemd releases the command was `systemd-resolve --status`; `resolvectl` replaced it.

## Step 2: Ask each server directly

```bash
dig @10.0.0.2 api.example.com +short     # your real upstream
dig @1.1.1.1 api.example.com +short      # a public resolver
dig @1.1.1.1 api.example.com +tcp +short # same, over TCP
```

How to read the results:

- **Upstream fails, public works:** the upstream DNS server is broken or doesn't know the name. Fix it there or point at a working one.
- **Both fail with a timeout:** outbound port 53 is blocked or routing is broken. Check the host firewall and security groups. See [how to check firewall status on Linux](/blog/check-firewall-status-linux).
- **UDP fails, TCP works:** something drops UDP/53 or large UDP responses. Usually a firewall or MTU problem.
- **Public works, but internal names only exist on the upstream:** don't "fix" this by switching to a public resolver. You'll lose internal names.

For a wider view of DNS inspection commands, see [how to check which DNS server Linux is using](/blog/how-to-check-dns-server-linux).

## Step 3: Fix it where the config comes from

Editing `/etc/resolv.conf` by hand works until the next reboot, DHCP renewal, or NetworkManager restart. Make the change in the layer that owns it.

### systemd-resolved with netplan (Ubuntu Server)

```yaml
# /etc/netplan/50-cloud-init.yaml (or your own file)
network:
  version: 2
  ethernets:
    eth0:
      dhcp4: true
      dhcp4-overrides:
        use-dns: false
      nameservers:
        addresses: [10.0.0.2, 10.0.0.3]
        search: [corp.example.com]
```

```bash
netplan try          # auto-reverts in 120s unless you confirm
resolvectl status    # verify the new servers on the link
```

> **Warning:** a netplan mistake can take the interface down. On a remote box use `netplan try` rather than `netplan apply`, and have console access.

If you just need a global server and don't want to touch per-link config:

```ini
# /etc/systemd/resolved.conf.d/dns.conf
[Resolve]
DNS=10.0.0.2 10.0.0.3
```

```bash
systemctl restart systemd-resolved
```

If the symlink is broken or replaced by a plain file, restore it:

```bash
ln -sf ../run/systemd/resolve/stub-resolv.conf /etc/resolv.conf
```

### NetworkManager (RHEL, Rocky, Alma, Fedora, desktops)

The connection name is often not the device name. Look it up first:

```bash
nmcli -t -f NAME,DEVICE connection show --active
# System eth0:eth0

nmcli connection modify "System eth0" ipv4.dns "10.0.0.2 10.0.0.3" ipv4.ignore-auto-dns yes
nmcli connection up "System eth0"
```

`ipv4.ignore-auto-dns yes` stops DHCP-provided servers from being added back. `connection up` re-activates the interface, which can blip your SSH session. Run it inside `tmux` or with console access.

### Split DNS: internal domain to the internal server

You want `*.corp` to go to `10.0.0.53` and everything else to the normal upstream. With systemd-resolved:

```ini
# /etc/systemd/resolved.conf.d/corp.conf
[Resolve]
DNS=10.0.0.53
Domains=~corp
```

The `~` makes it a routing domain only. It is not added to the search list. Restart `systemd-resolved` and check with `resolvectl query app.corp`.

### Cloud instances

Cloud VMs usually get a provider resolver via DHCP. On AWS this is the VPC resolver at the VPC base address +2 (also reachable at `169.254.169.253`), and it is what makes private hosted zones and `*.internal` names work. Replacing it with `8.8.8.8` "fixes" public names and silently breaks private ones. Add servers instead of replacing them, or fix the DHCP options at the VPC level.

## Docker containers can't resolve

```bash
docker exec app cat /etc/resolv.conf
docker exec app getent hosts example.com    # if the image has getent
```

What Docker actually does:

- **Default bridge network:** the container gets a copy of the host's `resolv.conf` with loopback servers removed. If the host uses the systemd-resolved stub (`127.0.0.53`), Docker reads the real upstreams from `/run/systemd/resolve/resolv.conf`. If no usable servers remain, it falls back to `8.8.8.8` and `8.8.4.4`, which corporate networks often block.
- **User-defined networks (Compose):** the container sees `nameserver 127.0.0.11`, Docker's embedded DNS. It resolves container names and forwards everything else to the host's upstreams.

So "DNS works on the host but not in the container" usually means the fallback public servers are blocked, or a host firewall drops forwarded traffic from the bridge. To set servers explicitly:

```bash
docker run --dns 10.0.0.2 myimage
```

Or daemon-wide, in `/etc/docker/daemon.json`:

```json
{
  "dns": ["10.0.0.2", "10.0.0.3"]
}
```

> **Warning:** merge this key into your existing `daemon.json`; don't overwrite the file, or you lose log rotation and other settings. Restarting Docker restarts running containers unless `live-restore` is enabled.

More on how container networking fits together: [Docker networking guide](/blog/docker-networking-guide).

## Clear caches after the fix

A fixed config can still serve stale or negative answers for a while:

```bash
resolvectl flush-caches          # systemd-resolved
resolvectl statistics            # cache size, hits/misses
nscd -i hosts                    # only if nscd is installed
```

Applications cache too. Java caches successful lookups (30 seconds by default when no security manager is installed), and many HTTP clients reuse connections. If one service still fails after the host resolves correctly, restart that service before digging further.

## Checklist

1. Compare `getent ahosts` with `dig`. Disagreement means a local layer (hosts, nsswitch, search domain).
2. `ls -l /etc/resolv.conf` tells you who manages DNS. Fix it there, not in the file.
3. `resolvectl status` shows the real upstream behind `127.0.0.53`.
4. `dig @upstream` vs `dig @1.1.1.1` splits "bad server" from "blocked network".
5. Containers: check `/etc/resolv.conf` inside the container and whether the fallback servers are reachable.
6. Flush caches and restart the affected service.

## FAQ

**Why does dig work but my application can't resolve the name?**
`dig` queries the nameserver directly and skips `/etc/hosts`, `nsswitch.conf` and search domains. Applications use all of them. Test with `getent ahosts <name>`, which follows the same path an application does.

**How do I make DNS changes in /etc/resolv.conf permanent?**
Don't edit the file if something manages it. On systemd-resolved systems use netplan or `resolved.conf.d`. On NetworkManager systems use `nmcli connection modify`. Only edit the file directly when nothing else writes to it.

**Why can't I resolve .local hostnames?**
On many desktops `nsswitch.conf` sends `.local` names to mDNS and stops if mDNS has no answer (`[NOTFOUND=return]`). If your company DNS uses `.local`, move `dns` before `mdns4_minimal` or remove the `[NOTFOUND=return]` action.
